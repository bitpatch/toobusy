# Architecture

This describes how the code is laid out and why. The behaviour of the tool is described in [IDEA.md](IDEA.md) and, part by part, in [SPEC.md](SPEC.md). The settings, the setup, the doctor and the run are the parts that exist.

## Projects

```
src/
  TooBusy.Core/                    domain and use cases; depends on nothing
  TooBusy.Infrastructure/          processes, git, the files of the settings and of a run, operating system services
  TooBusy.Trackers.GitHub/         task tracker adapter: GitHub Issues and Projects
  TooBusy.Assistants.ClaudeCode/   assistant adapter: Claude Code
  TooBusy.Cli/                     composition root, commands, console; the `toobusy` binary
tests/
  TooBusy.Architecture.Tests/      the dependency rules below
  TooBusy.Assistants.ClaudeCode.Tests/
  TooBusy.Cli.Tests/
  TooBusy.Core.Tests/
  TooBusy.Infrastructure.Tests/
  TooBusy.Trackers.GitHub.Tests/
```

A test project is added together with the first code of the project it tests.

## Dependency rules

- `TooBusy.Core` references no other project and no package that reaches outside the process.
- `TooBusy.Infrastructure` and every adapter reference `TooBusy.Core` only. Adapters do not reference each other.
- `TooBusy.Cli` references everything and is the only place where implementations are chosen and wired together.

`TooBusy.Architecture.Tests` reads the project files and fails when a project reference breaks these rules; the packages of a project are not checked there. A new project needs a rule there.

## Core and its ports

`TooBusy.Core` holds the model (task, queue, outcome, limits, settings) and the use cases (the setup, the queue, the run). Everything outside the process is reached through an interface that Core defines and another project implements:

| Port | What it hides | Implementations |
|---|---|---|
| `ITaskTracker` | reading the open tasks, and a closed one by its number, and changing one: its status on the board, its assignee, its labels, a comment, closing. It makes no task: a session does that itself. A call that fails throws `TrackerException`, which says whether the failure may pass, as when GitHub did not answer, or stays | `GitHubTasks` in `TooBusy.Trackers.GitHub`; `ImitatedTasks` in a demo |
| `IAssistant`, `IAssistantSession` | starting a session with a message, looking at it, telling it something more, asking it something without cutting its turn, which throws `LocalStateException` when the request cannot be left where the session reads it, stopping it; finding the session of an earlier run by what was kept of it, a `SessionTrace`, and the one a start that was cut off may have left, by the name of the start and when it was made; the limits of usage | `ClaudeCode` in `TooBusy.Assistants.ClaudeCode`; `ImitatedAssistant` in a demo |
| `IWorkspace` | the working copy: how many files differ from what is committed, how many commits are not pushed, which branch is checked out; and bringing that branch up to date with its upstream, a `BranchSync`, which says of a remote that could not be fetched whether that may pass | `GitWorkspace` in `TooBusy.Infrastructure`; in a demo one that is always clean and level, inside `ImitatedRun` |
| `IProcessRunner` | running a command with a timeout and cancellation, in a folder | `ProcessRunner` in `TooBusy.Infrastructure` |
| `IProjectCommands` | running a command of the project through the shell of the machine, at the root of the working copy, with what it is told of a task in its environment, and what it printed | `ShellCommands` in `TooBusy.Infrastructure`; in a demo one that is never asked, inside `ImitatedRun` |
| `IClock` | the time, and waiting | `SystemClock` in `TooBusy.Infrastructure` |
| `IMachine` | keeping the machine awake, notifying the owner | `LocalMachine` in `TooBusy.Infrastructure`; in a demo one that does neither, inside `ImitatedRun` |
| `IRunState` | what a run leaves for the next one: the record of the task it has a session for, a `TaskRecord`. A record that cannot be read is none; one that cannot be written or forgotten throws `LocalStateException`, with words that say which and what the system said | `RunStateFile` in `TooBusy.Infrastructure`; `UnwrittenState` in a demo |
| `IRunSign` | the sign a run puts up in the working copy for as long as it goes on: putting it up, which gives the sign of another run that goes on there instead, saying anew what the run does, and taking it down. Each of these throws `LocalStateException` when the sign cannot be written or taken down | `RunSignFile` in `TooBusy.Infrastructure`; in a demo one that puts nothing up, inside `ImitatedRun` |
| `IRunView` | where a run tells what happens: the lines of its log, every task that is over, and what it is doing now | `RunFeed` and `PlainRun` in `TooBusy.Cli` |

Core is tested with hand-written fakes of these ports. A demo is such a fake offered to the user: imitated tracker and sessions behind the same ports.

Sessions are identified by the task they belong to, and the ports of the tracker and of the assistant do not assume that only one runs at a time. `IRunState`, `IRunSign` and `IWorkspace` do, as they are now: the first keeps the record of a single task, the second is the sign of the one run of a working copy, the third reads a single working copy. The first version runs one session; parallel sessions in git worktrees must fit the same ports, with a record and a working copy for each.

## Run

`TooBusy.Core/Queue` holds the queue. `TaskLineup.Arrange` is its rules, a function of the open tasks and of `QueueRules`, which come from the settings, with the labels a run was told to skip besides: the tasks that can be taken now and their order, those that open as others close, and those that are held, each with its reason. `Holds` says of one task why a run does not take it now, for a run that was started for that task.

`TooBusy.Core/Run` holds the run:

- `Supervisor` is the run itself, behind `IQueueRun`: the loop over the tasks, the watching of a session, the limits, the pause, and telling the tracker how a task went. It writes the record of a task when its session starts and whenever what the session is found by changes, and forgets it at an outcome; before the queue it looks at the record of an earlier run, and goes on with that session in the way it was left: `TaskLineup.Recorded` says whether the task is still gone on with, and `Taking` puts it before the others. Before all of that it puts up the sign of the run, a `RunSign`, and starts nothing when the sign of another run is given back; it says anew on the sign what it shows of itself, when that changes what the sign says, and takes the sign down however the run ends. No exception leaves it: a `TrackerException`, an `AssistantException` and a `LocalStateException` stop the run with their words, and anything else, a cancellation that is not the kill among it, stops it as a problem too, with the kind and the words of the error in the log. Where a session works, the scope of the task stops the session first, so that no failure leaves it working with nobody watching: a file of the run that cannot be written stops the run right there, with the session named, and anything else is said and thrown on to `RunAsync`. A sign that cannot be written is not tried again while the run ends over it, and one that cannot be taken down is only said. It is one flow of control. Commands reach it through `Send`, which only puts them in a line that the run looks at in one place, so nothing in it is shared between threads; a kill is the cancellation of the run. A run that is started for one task refuses it there, before anything is started, when the lineup does not have it ready or the record names another task; one that is started for a number of tasks counts those that came to an outcome. Both end as a run that its owner stopped, with what ended them as the `Why` of the result. The commands of the project stand around the doing of a task in one place, `DoAsync`: the one before it where the task is about to be touched, and the one after it when the run has done with the task, whatever it returned or threw. The branch of the settings is checked where the working tree is, before the queue is read, and brought up to date with its upstream, by `BringUpAsync`, right before the command before a task that is taken anew; a task of the record is not, as its session may have left its changes in the working tree. A call of the tracker that is safe to make twice goes through `AgainAsync`, by one of the methods that name it in words, as `MoveAsync`: a `TrackerException` that may pass makes it again after each of the `RetryPauses` of the policy, with a line of the log before the try, and the last failure is thrown as it is. A comment goes to the tracker directly and is made once. A kill ends a pause, and after a kill nothing is made again. A kill leaves no task half moved: a kill during the start of a session sends the task back and stops a session the start left, found through `FindStartedAsync`, and once the record of a task is forgotten, as when the tracker is told how it went, and in a pause, the calls of the tracker are made uncut, so that they go to their end; `DoAsync` ends the run as killed when such a task is over, unless the task stopped it over a problem. An uncut call whose pause a kill ends fails with the failure it had. `BringUpAsync` makes the sync again by the same pauses when the remote did not answer. Everything it knows of time comes from `IClock`, so the tests run it start to finish in no time, with a clock that moves only when it is waited on.
- `Outcome` is the line for toobusy at the end of a reply: the contract with the assistant, read here, whether a reply ends with it, with nothing but empty lines after it, and whether the report before it names another task, as one of a task done in part must. Its words are written out once more only in the plays of a demo, which are replies as a session would give them.
- `Briefing` is every text toobusy sends to a session, and what it writes into the tracker from what the session answers. The texts are those of the tool and know nothing of a project but what the settings name: the first message begins with the command of the skill of the project, when it has one, and is the same after it.
- `About` is what `toobusy about` prints: how a run works, put together from the messages of `Briefing`, the lines of `Outcome`, the policy and, where there are settings, the rules of the queue, the skill, the branch and the commands around a task, so that it tells what a run does and nothing else.
- `RunPolicy` is the times and the counts of a run, the pauses before a call of the tracker or a fetch is made again among them; a demo has its own. `RunPlan` is what the user and the settings give it: the milestone, the rules of the queue, the model and the effort, the address of the board, the skill a session starts with, the commands of the project around a task, the branch the tasks are done on, the permission mode its sessions work in, which only its log says, and, from the options of `toobusy run`, the one task it does or the number of tasks it takes at most, and the labels it skips, which stand in its rules of the queue: `TaskLineup.Keeps`, which says whether the task of a record is gone on with, does not look at them. `NewTasks` is what of it a session is told to make a new task: the manual label, the labels to take, the milestone and the board.
- `RunLine`, `TaskEnd` and `RunStatus` are what a run tells: a line of its log with the mark of what it tells; a task that is over, told once however it ended, with its mark and the time it took; and what the run is doing now, with the commands that mean something at the moment and, while a session waits for the owner, what the session said. `RunResult` says how the run ended and, when it neither ran out of tasks nor was stopped by a command of its owner, why. `RunSign` is what of a `RunStatus` stands on the sign of a run: where the run is, its task, how the session is opened and until when it waits for a usage limit; `Told` says it in a few words, the same for `toobusy status`, for a run that does not start and for the menu.

The adapters know their tools and nothing of a run:

- `GitHubTasks` asks `gh` as the other GitHub adapters do, and the tool itself turns the answers into lines of tab-separated fields. A failure is a `TrackerException` with the first line `gh` said, and it may pass when `gh` did not answer in its time or what it said tells a call that did not reach GitHub, a status of the 500s, a 429, or a rate limit; every other failure stays. The other GitHub adapters say nothing of that: the commands they serve are run by a person, who runs them again. The statuses of a board are known by the names the settings give them, each the name of GitHub where the settings name none, whatever their case and whatever stands between their letters: `BoardStatuses` of `TooBusy.Core/Queue` is those three names. It tells which status a name of the board is and what a status is called, and says which of the three a board lacks, for the doctor and the setup. The settings hold one, `TrackerSettings.Statuses`, and it goes from there to whatever names a status: to `GitHubTasks`, which reads the status of a task by it and finds the option to move a task to, and through `QueueRules` to the log of a run, to `NewTasks` for the first message of a session, and to `About`. The queue itself knows no names: it takes a task whose `BoardStatus` is `Todo`, which the adapter has told by them. `GitHubSetup.ReadStatusesAsync` reads what a board calls its statuses, the options of its `Status` field, for the two of them and for any command that shows the boards.
- `ClaudeCode` does a task in a background session of Claude Code. It is made with the permission mode of the settings, and starts every session in it and goes on with every session in it, one of an earlier run too: the mode belongs to the adapter, and is not passed with a session. `ClaudeFolders` is where its files are; `SessionSettings` is the settings a session is started with: a hook that prints the request of the run after every step, a status line that writes the state of the session, the limits among it, to a file, and no worktree. `Transcript` reads the conversation Claude Code writes, from where the reading stopped: the steps of the session; its last reply, and whether the session has reported with it, which a look gives as `Reported`: the reply ends with the line for toobusy, as `Outcome` reads it, and the session did nothing after it; a usage limit; and, from its start, the plan the session keeps as a list of tasks, which a look gives as `PlanStep`s. The session is found in `claude agents --json --all`. A session of an earlier run is found there too, by its id, the one `claude attach` takes, or by its conversation; one that is not there is lost at once, and nothing is left of one that no process has and whose conversation is not on the machine. The session of a start that was cut off is the one of the list with the name the start gave it, `-n`, and started since the start was made; the list is read a few times for it, as a session that has just started is not always listed at once. When a session is told something, what it said before does not count any more. `ClaudeSkills` says whether a skill is there for Claude Code to load by its command: among the skills and the commands of the project, or among those of the user.
- `GitWorkspace` reads the working copy from `git status --porcelain=v2 --branch`: the files, the branch, its upstream and the commits each has that the other lacks. It brings the branch up to date with `git fetch`, which fetches the remote of the branch, and `git merge --ff-only @{upstream}`, which can only move it forward, and only after it has counted the commits again: a branch with commits of its own is not merged at all. A fetch that failed may pass when it did not end in its time, or when what git and ssh said tells a remote that was not reached or answered with a status of the 500s or a 429.
- `ShellCommands` runs a line through `sh -c`, or `cmd /c` on Windows, apart from `ProcessRunner`, which starts a command without a shell: it gives the command an environment, keeps what it printed to both streams as one text, also of a command that is stopped for its time, and does not wait for what a command left running with its output open.
- `LocalFolder` is `.toobusy/local` of a project, which keeps itself out of git with a `.gitignore` of its own. `RunStateFile` is the record there, `session.json`, put in place whole. `RunSignFile` is the sign of a run there, `run.json`, with the number of the process of the run and when that process started: it reads a sign as a `GoingRun` only while that process lives and started then, which it asks the operating system through `System.Diagnostics.Process`, so what a run that died left behind is not read, and it takes down no sign but its own.

`Workbench.OpenRun` puts a run together: the real adapters, or `ImitatedRun`, the real `Supervisor` over made-up tasks and sessions that are plays written in the code, lasting as long as the clock says.

## Settings

The settings of a project live in three places:

- `TooBusy.Core/Settings` holds the model (`ProjectSettings`), the names of the keys (`SettingsKeys`) and the validation rules (`SettingsValidator`). The validator knows nothing of TOML: it takes a `SettingsDocument`, every value under its full dotted key with the line it is written on, and gives back the settings or the errors, each with its key and, where the file has a place for it, its line.
- `TooBusy.Infrastructure/Settings` reaches the disk. `ProjectLocator` walks up to the root of the git working copy, `SettingsFile` is `.toobusy/settings.toml` at that root, and `SettingsToml` turns TOML text into a `SettingsDocument` and settings back into text.
- `TooBusy.Cli` asks for the project and its settings before a command runs, prints the "not set up" message, and maps the outcomes to the exit codes in `ExitCode`. `CliApp.RunAsync` says an error that a command did not foresee in a `toobusy:` line where errors go and exits with code 1, instead of the stack trace of `System.CommandLine`; `Guarded`, around the action of every command that can be cancelled, tells such an error from the cancellation of the user, which it lets through. The trace is printed when `CliContext.Trace` asks for it, which is `TOOBUSY_TRACE=1`.

TOML is parsed with [Tomlyn](https://github.com/xoofx/Tomlyn), through its syntax tree only (`SyntaxParser`): the tree keeps the place of every value, and nothing of it needs reflection. The object serializer of Tomlyn is not used. Writing does not print the tree: `SettingsToml.Write` edits the existing text at the places the tree names, replacing a value that differs, removing the line of a key the settings have no more, adding a missing key at the end of its section, or before everything else when it has no section, and a missing section, with its comment, at the end of the file. Everything else, comments and unknown keys included, stays character for character, and a new file is the same edit of an empty text. The result is parsed again before it is returned; a layout that cannot be edited this way, such as a section written as an inline table, is refused with a `FormatException` instead of being written wrong, and so is a text that is not TOML. `SettingsFile` then writes the file anew, as it writes a first one.

## Setup

`TooBusy.Core/Setup` holds the steps of `toobusy init` (`ProjectSetup`) and the ports they are written against, but for the store of the settings, which stands with the settings:

| Port | What it hides | Implementations |
|---|---|---|
| `ISetupDialog` | showing the notes, the answers and the place among the steps; asking: a selection, a multiple choice, a text, the board, a confirmation; waiting for something that is read. Every question can be gone back from, and so can a wait: the reading is told to stop | `SetupScreen` in `TooBusy.Cli`; a scripted one in the tests; none for `init --yes`, where `ProjectSetup` takes what every question proposes |
| `ISetupEnvironment` | what is installed and logged in, the `origin` remote, and whether a skill is there, a `SkillLook` | `MachineEnvironment` in `TooBusy.Cli`, which runs the checks of the doctor that need no settings, adds the `origin` read by `GitOrigin` of `TooBusy.Infrastructure` and asks the machine of the doctor for the skill; imitated in a demo, where every skill is there |
| `ISetupTracker` | whether a board can be read, what it calls its statuses, the labels; making a board, linking one to the repository and making a label, which throw `TrackerException` when GitHub refuses | `GitHubSetup` in `TooBusy.Trackers.GitHub`; imitated in a demo |
| `ISetupBoards` | the boards the user can reach, those linked to the repository, and who a new one can belong to | `GitHubBoards` in `TooBusy.Trackers.GitHub`, which asks `gh` through `IProcessRunner`; in a demo `ImitatedBoards`, which adds made-up ones to them |
| `ISettingsStore`, in `TooBusy.Core/Settings` | the settings file: loading, the text before and after a change, saving | `SettingsFile` in `TooBusy.Infrastructure`; in a demo `UnwrittenSettings`, which remembers instead of writing |

`TooBusy.Core/Queue` holds the milestone to work on. It is the choice of the user, not a setting of the project. `TooBusy.Core/Assistant` holds two more such choices, the model and the effort the tasks are done with by default: `ModelChoice`, and `ClaudeCodeOptions` with the models and the levels that are offered. `ClaudeCodeOptions` holds the permission modes a session can be started in too, which are a setting of the project and not a choice of the user, with why the others are refused. The lists are those of Claude Code, the only assistant so far, and they stay in Core until the port of the assistant is asked for them. The choices have two ports:

| Port | What it hides | Implementations |
|---|---|---|
| `IMilestones` | the open milestones of a repository | `GitHubMilestones` in `TooBusy.Trackers.GitHub`; in a demo `ImitatedMilestones`, which adds made-up ones to them |
| `IPersonalSettings`, in `TooBusy.Core/Settings` | where the choices of the user are kept: the milestone, the model and the effort, each one apart | `PersonalSettingsFile` in `TooBusy.Infrastructure`: `projects.toml` of the user's own toobusy folder, a table for each project; in a demo `UnsavedChoice`, which forgets |

`MilestoneStanding` says where a choice stands against the open milestones: not made, open, no milestone, gone, or not checked because the milestones cannot be read. `MilestoneOrder` is the order milestones are offered in.

`ProjectSetup` is a walk over its steps: an answer moves it forward, going back from a question moves it to the step before, and going back from the first one leaves the setup. It keeps the answers, so that a step that is asked again proposes what was answered. Nothing is changed before the last step is confirmed; a new board is an answer like any other until then.

The same steps serve `Settings` of the menu one setting at a time. `OpenAsync` looks at the machine and reads the settings as the walk does, `Values` are the settings as the menu lists them, a `SetupValue` for each `SetupSetting` with how its value looks, the statuses of a board among them as `BoardStatuses.Told` says which is which, and `ChangeAsync` asks the questions of one setting with the answers of the others as the settings have them: the questions of `init`, those of the statuses whatever the board calls them, and for the commands around a task, the branch and the permission mode questions of their own. What is answered goes through the same last page, which in the menu decides by the settings whether anything changes, does on GitHub only what that setting needs, and asks `Save the change?`; going back from it asks the setting again. `SetupProgress.Menu` tells the dialog that a question is of such a setting: there are no steps, and going back from its first question gives what is chosen or typed there as the answer, so that a setting that is left changed is asked about too. A question of the labels offers every label with its roles in the other settings, a `SetupOption` that is off where a role keeps it out, as `RolesOf` tells: in the menu by all the other settings, in the walk by the steps before it, whose order keeps the answers right. The menu keeps the manual label out of the blocking labels, where it keeps out nothing more. `Changed` is what the menu saved, for the report.

The options of `init` reach the steps as `SetupProposals`: what an option says is proposed before the value of the settings and before what a first setup proposes. The board of an option is checked when the boards are read and its labels when the labels are, once. `--yes` is the same walk without a dialog: `ProjectSetup` then answers every question with what it proposes and the last one with a yes, so a setup that asks nothing does what one does where Enter is pressed all the way. The question about the board is where the two can differ: with no board to keep and none proposed, the screen opens on the list of the boards, where Enter takes the first of them, and a setup that asks nothing takes no board. What an option says and cannot be is a warning among the notes where somebody is asked, and where nobody is it ends the setup as failed, before anything is changed; so does a proposed text that its question refuses, and a board that cannot be read. The result carries the notes and a line for each thing that was done on GitHub, which `CliApp` prints as plain lines.

The setup never asks for the repository: `ISetupEnvironment` gives the one of the `origin` remote, and the labels are read from it. A board that is chosen has its statuses read through `ISetupTracker`, and the step of the board goes on with which of them is which: three questions of the same step, asked through `ISetupDialog` as a choice among the statuses, or as a typed name where nothing is verified, and not asked at all over a board that has the names of GitHub. `SetupProgress.Later` tells the dialog that such a question is not the first of its step, so that going back from it does not leave the setup. A board that cannot be asked about, with fewer than three statuses or in a setup that asks nothing, is taken with a warning on the last page and among the notes of the result. Nor does it make the skill it asks the name of: it asks `ISetupEnvironment` whether the skill is there, and says where it is to be written when it is not. `BoardSuggestions` is what the question about the board does with a typed text: it finds the boards that fit it and turns the address of any page of a project into the address of its board.

`Assist` is what `toobusy init --assist` prints: the walk through the setup for the assistant of the owner. It stands beside the setup as `About` stands beside the run: a function of how the project stands, an `AssistGround`, that gives the text of the introduction or of one step, with nothing of the terminal in it. The ground is the settings as they were loaded, the choices of the user, what is found of the skill, what the sign of a run says, and, for a step that chooses among what the tracker has, one reading of it: `Assist.Reads` says which, the labels, the boards with their statuses or the open milestones. What a command of a step proposes to call the two labels and the skill is what `ProjectSetup` proposes in a first setup. `Workbench.AssistAsync` reads the ground through the ports the setup and the doctor read through, and changes nothing; it asks whether `gh` is there and logged in before anything of the tracker, so that a step can say why something is not read. `CliApp` checks the number and that no other option stands beside `--assist`, and opens no demo for it.

`Workbench` in `TooBusy.Cli` is where these ports are put together for a project, in one place: the real adapters, or, for `--demo`, the imitations of `TooBusy.Cli/Imitation`. A demo is the real steps and the real screens over a machine where everything is installed, a tracker with made-up labels, whose boards have the three statuses, that makes and links nothing, settings that are read from the file and remembered instead of written, and choices of the milestone, the model and the effort that are forgotten when the demo ends. The demos that show a project that is ready, `toobusy --demo`, `run --demo` and `doctor --demo`, make the settings up where there is no file, and start with the choices made. The `origin` remote, the boards and the milestones are not imitated: they are read through `git` and `gh`, which changes nothing, and made-up boards, owners and milestones are added after the real ones until there are enough to scroll.

`Session` is what happens on the page from the moment it is opened: the setup when the project needs it, the choices of the milestone, the model and the effort when the user has none, the menu and the run, each a screen that takes the page for a while. A run that is opened from the menu comes back to it; `toobusy run` runs the queue alone and leaves. `Settings` of the menu opens one `ProjectSetup` for as long as its list is on the page, and a `SettingsScreen` over it; settings that do not validate get the walk of `init` instead, as a project that is not set up does. What it saved is the setup the report tells, kept as soon as a change is saved. Before the menu opens a run, outside a demo, `Session` makes the checks of the doctor and gives them to the menu as `RunChecks`, the view of the checks that the menu watches; the checks that failed go into the body of the page, above the menu, as the lines `CheckList.Told` makes of them. An error that stops the checks, other than the stop of the menu, is one more check that failed, so that the menu opens no run where `toobusy run` would start none. The setup of `Settings` is opened in the same way, under the menu, as a `HomeWork`: both are an `IHomeWait`, what a row of the menu waits for before it opens, which `HomeScreen.WaitAsync` shows at its row until the wait is over and the menu gives that row by itself. Another row that is chosen meanwhile is what `Session` goes on with, and Escape gives nothing and the menu is asked again; either way the work that was not waited for is told to stop and left to it. A screen of it that says nothing at the right of the bar, as the menu, says the version of the tool there: `CliApp.Version`, the one place the version is read from, which `--version` prints too, with `CliApp.Commit` after a plus in a build in development. It remembers what was done for the report that `CliApp` leaves in the terminal, which says nothing of a run again: a run leaves its own tape there. `Workbench.ReadQueueAsync` reads the queue as a run does before a task and changes nothing: the lineup, with the task of the record before the others when a run would go on with it. `Workbench.OutlookAsync` says from it what a run would take, for the menu: how many tasks, and the one it goes on with first, the task of the record or an interrupted one. Both take the labels a run skips: those of `run --skip-label` and `queue --skip-label`, or those `Session` keeps from `Skip labels` of the menu for as long as the page is open, and nowhere else. `Workbench.ReadLabelsAsync` reads the labels that the menu offers to skip, as the setup reads them, after it has asked whether `gh` is there and logged in, so that the list can say why it has none. `toobusy queue` prints the same lineup whole. `Workbench.Going` is the run that goes on in the working copy, by its sign: `toobusy run` and `Run` of the menu ask it before the checks and open no run while there is one. `toobusy status` asks for no `Workbench`: it reads the sign and the record of the local folder and nothing else.

## Doctor

`TooBusy.Core/Doctor` holds the checks of everything a run needs. `Checkup` runs them in their order and knows which check waits for which: `MachineAsync` is the five that need no settings, the tools and their logins, and `RunAsync` adds the settings, the repository, the board, its statuses, the labels and the skill a session starts with. A check ends as a `CheckResult`: passed, failed or skipped, with what it found or what is wrong and, for a failure, its fix. `Fixes` is the table of the fixes, a function of the tool, the platform and whether its package manager is there. The checks read the settings through `ISettingsStore`, and have two ports of their own:

| Port | What it hides | Implementations |
|---|---|---|
| `ICheckupMachine` | the platform; whether `git`, `gh` and `claude` run and whether a package manager is on the path; the logins of the tracker and of the assistant; whether the repository and the board can be read; what the board calls its statuses; the labels of the repository; whether the assistant has a skill | `MachineCheckup` in `TooBusy.Cli`, which asks the tools for their versions through `IProcessRunner` and puts together `GitHubCli` and `GitHubSetup` of `TooBusy.Trackers.GitHub` and `ClaudeLogin` and `ClaudeSkills` of `TooBusy.Assistants.ClaudeCode`; in a demo `ImitatedCheckup`, a machine that has it all |
| `ICheckupView` | where the checks tell that one starts and how each ends | `CheckList` in `TooBusy.Cli`; `NoCheckupView` where nobody watches, as in the setup |

`Workbench.Checkup` puts them together over the settings and the `origin` remote of the project. `toobusy doctor` shows every check, `toobusy run` and `Run` of the menu run them before a run starts and tell the failures only, and `MachineEnvironment` turns the failed ones of the machine into the notes of the setup.

## Terminal

`TooBusy.Cli/Terminal` is everything that knows it talks to a terminal.

- `Palette` is the one place that defines colours: the accent, the error, success, the warning and muted text, each for a dark and a light terminal in truecolor, and as one of the sixteen colours for a terminal that does not announce truecolor. `Palette.Detect` gives the palette without colours when `NO_COLOR` is set or the stream is not a terminal. Commands never write an escape sequence of a colour themselves.
- `TerminalDevice` is the terminal as a screen needs it: its keys, its size, taking Ctrl+C as a key, watching the size of the window, and a timer.
- `Screen` is the alternate screen, entered with the first frame that is drawn. It draws a frame whole every time: the bar with the title and the status, the body, the question, the choice and the keys with a rule between them, and the foot, each line cut to the width. What waits for the user is drawn by the screen and blinks: the name on the chosen line of the choice, which is the first piece of that line, and the block where a text is typed. `Pulse` counts the beats, eighty milliseconds each, and rewrites only that line and that cell in the shade of the moment; drawing a frame does not start the count again. The same beat moves the light along the dots of a wait, the line that `Page.WaitAsync` puts under what is being read: `Screen.Spark` says how brightly a dot is lit at a step. The foot is wrapped to the width, never cut. `TerminalDevice.Every` is the timer behind it, so that tests move the pulse by hand. It keeps the last frame to draw it again when the size changes. The dots of a wait may stand after a name on a row: the screen finds them in the line. `Screen.Rescue` is what a program that is stopped from outside must still write, whatever has the terminal at the moment.
- `Tape` is the terminal's own screen written as a tape, for a run: `Screen.Unroll` leaves the alternate screen and prints the bar once; what is settled is written for good and scrolls into the history of the terminal, and the foot, a `Strip`, is drawn over itself under it: the cursor goes up to its first line, every line is written again, and what is left of a longer foot is erased. Nothing above the foot is erased while the window keeps its size. The tape remembers what it has settled, as pieces that lay their lines out to a width: when the size of the window changes it erases the terminal with its history and writes the bar, all of them and the foot anew. Lines are cut a column short of the window and the terminal is told not to wrap, because a line the terminal broke would make the foot taller than it is counted. The tape shares the lock and the beat of the screen: the mark of the foot turns, and its chosen line, its cursor and the lit cells of a bar blink, written where they stand by moves counted from the line the cursor rests on. The next frame rolls the tape up and enters the screen again.
- `Page` is what every screen of the tool shares: it takes the terminal and gives it back, puts the body, the status and the foot it is given around the question of the moment, and reads the keys. Ctrl+C twice in a row throws `OperationCanceledException`, which the command that opened the page catches. While more keys are waiting, as in a paste, it does not draw. `WaitAsync` runs something that takes a moment under the dots of a wait and goes on reading the keys meanwhile, looking for one every thirty milliseconds, so that `Back`, Escape and Ctrl+C work before the work ends; work that is not waited for gets its cancellation and is left behind.
- `SetupScreen` is the setup on a page, `MilestoneScreen` the list of the milestones, `ModelScreen` and `EffortScreen` the lists of the models and of the levels of effort, `HomeScreen` the menu, `AssistantScreen` the list its `Assistant` opens, `SettingsScreen` the list its `Settings` opens, every setting with its value, and `SkipScreen` the multiple choice its `Skip labels` opens.
- `RunScreen` is the page of a run, on a `Tape`: the tasks that are over and what the run warns of stay, and the foot is the task that is worked on, with the plan of its session as a bar under it, the menu of the commands between two rules, whose pointer says where the menu opens or that the run stops or aborts, with the usage limits at its right, and the keys with the place of the task among the tasks of the run, which `RunStatus` gives as the tasks over before it and those that follow it. The run goes on by itself on another thread and never touches the page: it speaks into a `RunFeed`, and the page takes from there what was said when it draws. The page waits for a key with `Page.ReadAsync`, which looks for one again and again and gives up when something changed, so that the foot is drawn anew; a foot that would show the same is not drawn. When the run is over the page writes how it went and gives the result; however the page is left, the run is killed and never left to go on alone. `RunLook` is what a run looks like: the lines of its log, the line of a task that is over, the bar of a plan, the summary. `PlainRun` prints the log where there is no terminal. `Picker` is the list the screens share: a row is a pointer, a name, what explains it and what is to be noticed about it, and a list that does not fit scrolls between marks. A choice may be off, and may wait: `PickAsync` draws the list again when what it waits for is done, as the menu does while the tasks are counted, and what goes on may choose a row by itself, as the checks before a run choose `Run` when they are over and the settings that are read choose `Settings`. Where Escape goes back and does not leave the page, a list ends with `Back`, which names its key: `Picker` adds the row by itself, and the lists that `SetupScreen` draws on its own ask it whether to. A `Choice` that is the one of now has `current` right after its name, in a column that the other rows of its list keep: a `SetupOption` of the setup says it is that one, a `BoardQuestion` names the board of the settings, and the lists of the milestone, the model and the effort know it from the choices of the user. `PickMany` is its multiple choice, of the setup and of `SkipScreen`: an option that is off is muted and is not chosen, and the mark of one that is current is in the colour of success, a steady `Part` among those that blink, as the `Blinking` of its line counts them. `Prompt` is the question that is answered with a text. Both can keep what is chosen or typed when they are left, for the first question of a setting of the menu: going back gives it as Enter does. `LineEditor` is the text of a field and the caret in it; it knows nothing of the screen.
- `CheckList` is the checks of the doctor as lines on the terminal's own screen, outside the alternate one: a mark, the name and what was found, and the fix under a failure. In a terminal the check that is running has a line with the sign of a tape, which turns with the same beat and is erased when the check ends; a list of failures only, as a run wants it, writes them where errors go and leaves nothing of the rest.
- `QueueLook` is what `toobusy queue` prints: the three lists of a lineup as lines, with the numbers and the titles in the same columns, and the same as JSON, written with `Utf8JsonWriter`. It has no screen: the lines go to the output as they are.
- `StatusLook` is what `toobusy status` prints: the line of a run that goes on, or that none does with the task of a record, and the same as JSON, written with `Utf8JsonWriter`; and the made-up run of its demo.
- `CliContext` carries the folder, the streams, their palettes, the terminal device, the process runner, the clock and the folder of the user's own settings into the commands, so that tests run them with string writers, scripted keys, a faked `git`, `gh` and `claude`, and a clock that makes nobody wait.

The screens are drawn by hand with the escape sequences every terminal knows. Spectre.Console was the first candidate and was not taken: the setup needs the whole window, with a panel that stays at its bottom, and its prompts write below one another.

The tests read a screen as text. What it looks like is checked with `tools/screenshot.py`: it runs the real binary in a pseudo-terminal, presses the keys of a scenario and draws the screen to pictures in `artifacts/screens`, the rows that blink at several moments of a blink. It is a Python script with its own environment for a terminal emulator and a drawing library; nothing of it is part of toobusy.

## Adding a tracker or an assistant

A new project `TooBusy.Trackers.<Name>` or `TooBusy.Assistants.<Name>` implements the ports and gets a rule in the architecture tests.

Nothing chooses an adapter by its name yet. `Workbench` puts the GitHub and the Claude Code adapters together whatever `tracker.type` and `assistant.type` say, and the validator lets them say `github` and `claude-code` only: the two names are constants of `SettingsKeys`. A second adapter brings that choice into `Workbench` and its name into `SettingsKeys`. Core changes with it, too, where it still knows the only tracker and the only assistant: the checks and the fixes of the doctor name `gh` and `claude`, the validator knows what the address of a GitHub board looks like, `RepositoryName` reads a GitHub remote, the steps of the setup write the two names, `About` names the folder Claude Code keeps the skills of a project in and tells what the permission modes of Claude Code check, the log of a run says that Claude Code marks a session as waiting for an answer and that GitHub did not answer, `Assist` tells of the files and the permission modes of Claude Code, and `ClaudeCodeOptions` holds the models, the levels and the permission modes of Claude Code. The validator knows the permission modes by the assistant of the settings, so a second assistant brings its own modes there.

## Native AOT

The tool ships as a native binary, so every source project is built with `IsAotCompatible` and warnings are errors. In practice:

- no reflection-based serialisation: JSON is read with `JsonDocument` and written with `Utf8JsonWriter`, and nothing is serialised from objects;
- no libraries that need runtime code generation or are not trim-safe;
- command-line parsing with `System.CommandLine`;
- TOML with the syntax tree of Tomlyn, which publishes without warnings;
- globalisation is invariant: output does not depend on the machine's culture.

A dependency is added only after checking that it publishes without AOT warnings.

## Conventions

- .NET 10, C# latest, nullable enabled, warnings as errors.
- Package versions live in `Directory.Packages.props`.
- Tests use xUnit v3.
