# Architecture

This describes how the code is laid out and why. The behaviour of the tool is described in [IDEA.md](IDEA.md) and, part by part, in [SPEC.md](SPEC.md). The settings, the setup, the doctor and the run are the parts that exist.

## Projects

```
src/
  TooBusy.Core/                    domain and use cases; depends on nothing
  TooBusy.Infrastructure/          processes, git, the files of the settings and of a run, operating system services
  TooBusy.Trackers.GitHub/         task tracker adapter: GitHub Issues and Projects
  TooBusy.Assistants.ClaudeCode/   assistant adapter: Claude Code
  TooBusy.Cli/                     composition root, commands, console; the `toobusy` binary
tests/
  TooBusy.Architecture.Tests/      the dependency rules below
  TooBusy.Assistants.ClaudeCode.Tests/
  TooBusy.Cli.Tests/
  TooBusy.Core.Tests/
  TooBusy.Infrastructure.Tests/
  TooBusy.Trackers.GitHub.Tests/
```

A test project is added together with the first code of the project it tests.

## Dependency rules

- `TooBusy.Core` references no other project and no package that reaches outside the process.
- `TooBusy.Infrastructure` and every adapter reference `TooBusy.Core` only. Adapters do not reference each other.
- `TooBusy.Cli` references everything and is the only place where implementations are chosen and wired together.

`TooBusy.Architecture.Tests` reads the project files and fails when a project reference breaks these rules, when Core has a package that is not let in there by name, when a project of `src` compiles a file from outside its folder or references an assembly as a file, and when a test project references another project than the one it is named after. A new project needs a rule there.

## Core and its ports

`TooBusy.Core` holds the model (task, queue, outcome, limits, settings) and the use cases (the setup, the queue, the run). Everything outside the process is reached through an interface that Core defines and another project implements:

| Port | What it hides | Implementations |
|---|---|---|
| `ITaskTracker` | reading the open tasks, and a closed one by its number, and changing one: its status on the board, its assignee, its labels, a comment, closing. It makes no task: a session does that itself. A call that fails throws `TrackerException`, which says whether the failure may pass, as when GitHub did not answer, or stays | `GitHubTasks` in `TooBusy.Trackers.GitHub`; `ImitatedTasks` in a demo |
| `IAssistant`, `IAssistantSession` | starting a session with a message, looking at it, telling it something more, asking it something without cutting its turn, which throws `LocalStateException` when the request cannot be left where the session reads it, stopping it, which throws `AssistantException` when the session still works after it; finding the session of an earlier run by what was kept of it, a `SessionTrace`, and the one a start that was cut off may have left, by the name of the start and when it was made; the limits of usage | `ClaudeCode` in `TooBusy.Assistants.ClaudeCode`; `ImitatedAssistant` in a demo |
| `IWorkspace` | the working copy: how many files differ from what is committed, how many commits are not pushed, which branch is checked out; and bringing that branch up to date with its upstream, a `BranchSync`, which says of a remote that could not be fetched whether that may pass | `GitWorkspace` in `TooBusy.Infrastructure`; in a demo one that is always clean and level, inside `ImitatedRuns` |
| `IProcessRunner` | running a command with a timeout and cancellation, in a folder; a command that is not on the path is told apart from one that is and cannot be started, which has why in its result | `ProcessRunner` in `TooBusy.Infrastructure`, which closes the input of a command and turns git's prompts off in its environment, as `Unattended` has them, reads what it prints as UTF-8, waits for its reads to end before it lets a command go that it stopped, and says in the system's words why a command could not be started, a folder that is not there among it; in a run `LoggedProcesses` around it, which writes every command into the log of the run |
| `IProjectCommands` | running a command of the project through the shell of the machine, at the root of the working copy, with what it is told of a task in its environment, and what it printed | `ShellCommands` in `TooBusy.Infrastructure`, with `LoggedCommands` around it in a run; in a demo one that is never asked, inside `ImitatedRuns` |
| `IClock` | the time, and waiting | `SystemClock` in `TooBusy.Infrastructure` |
| `IMachine` | keeping the machine awake, notifying the owner | `LocalMachine` in `TooBusy.Infrastructure`; in a demo one that does neither, inside `ImitatedRuns` |
| `IRunState` | what a run leaves for the next one: the record of the task it has a session for, a `TaskRecord`. A record that cannot be read is none; one that cannot be written or forgotten throws `LocalStateException`, with words that say which and what the system said | `RunStateFile` in `TooBusy.Infrastructure`; `UnwrittenState` in a demo |
| `IRunSign` | the sign a run puts up in the working copy for as long as it goes on: putting it up, which gives the sign of another run that goes on there instead, saying anew what the run does, and taking it down. Each of these throws `LocalStateException` when the sign cannot be written or taken down | `RunSignFile` in `TooBusy.Infrastructure`; in a demo one that puts nothing up, inside `ImitatedRuns` |
| `IRunView` | where a run tells what happens: the lines of its log, every task that is over, what it is doing now, and, as `Trace`, what only the log on disk keeps, how the run sees its session as that changes; a view without such a log leaves it, by default | `RunFeed` and `PlainRun` in `TooBusy.Cli`; in a run `LoggedView` of `TooBusy.Infrastructure` around either, which writes the lines into the log of the run |

Core is tested with hand-written fakes of these ports: those of the run are in `RunFakes.cs` of `TooBusy.Core.Tests`, and those of the setup, with the settings that the setup and the doctor share, in `SetupFakes.cs`. A demo is such a fake offered to the user: imitated tracker and sessions behind the same ports.

Sessions are identified by the task they belong to, and the ports of the tracker and of the assistant do not assume that only one runs at a time. `IRunState`, `IRunSign` and `IWorkspace` do, as they are now: the first keeps the record of a single task, the second is the sign of the one run of a working copy, the third reads a single working copy. The first version runs one session; parallel sessions in git worktrees must fit the same ports, with a record and a working copy for each.

## Run

`TooBusy.Core/Queue` holds the queue. `TaskLineup.Arrange` is its rules, a function of the open tasks and of `QueueRules`, which come from the settings, the `LabelSettings` of the queue and whether there is a board, with the labels a run was told to skip besides: the tasks that can be taken now and their order, those that open as others close, and those that are held, each with its reason. `Holds` says of one task why a run does not take it now, for a run that was started for that task.

`TooBusy.Core/Run` holds the run:

- `Supervisor` is the run itself, behind `IQueueRun`: the loop over the tasks, the watching of a session, the limits, the pause, and telling the tracker how a task went. It writes the record of a task when its session starts and whenever what the session is found by changes, and forgets it at an outcome; before the queue it looks at the record of an earlier run, and goes on with that session in the way it was left: `TaskLineup.Recorded` says whether the task is still gone on with, and `Taking` puts it before the others. Before all of that it puts up the sign of the run, a `RunSign`, and starts nothing when the sign of another run is given back; it says anew on the sign what it shows of itself, when that changes what the sign says, and takes the sign down however the run ends. No exception leaves it: a `TrackerException`, an `AssistantException` and a `LocalStateException` stop the run with their words, and anything else, a cancellation that is not the kill among it, stops it as a problem too, with the kind and the words of the error in the log. Where a session works, the scope of the task stops the session first, so that no failure leaves it working with nobody watching: a file of the run that cannot be written stops the run right there, with the session named, and anything else is said and thrown on to `RunAsync`. A sign that cannot be written is not tried again while the run ends over it, and one that cannot be taken down is only said. Every session is stopped through one method, `StopAsync`, which says a session that the assistant still has as working after it, for the owner to stop by hand, and goes on as it would. It is one flow of control. Commands reach it through `Send`, which only puts them in a line that one method, `Drain`, takes them from, at the turn of each of the loops of the run, over the tasks, of the watch of a session and of a wait, so nothing in it is shared between threads; a kill is the cancellation of the run. A command does something only where `Available` has it, the one rule of the commands that mean something at the moment, which the page of a run shows; otherwise the log says why it does nothing. A `Supervisor` makes one run: what it counts and what it was asked for are never reset, so a second `RunAsync` throws, and a second run is a new `Supervisor`. A run that is started for one task refuses it there, before anything is started, when the lineup does not have it ready or the record names another task; one that is started for a number of tasks counts those that came to an outcome. Both end as a run that its owner stopped, with what ended them as the `Why` of the result. The commands of the project stand around the doing of a task in one place, `DoAsync`: the one before it where the task is about to be touched, and the one after it when the run has done with the task, whatever it returned or threw. The branch of the settings is checked where the working tree is, before the queue is read, and brought up to date with its upstream, by `BringUpAsync`, right before the command before a task that is taken anew; a task of the record is not, as its session may have left its changes in the working tree. A call of the tracker that is safe to make twice goes through `AgainAsync`, by one of the methods that name it in words, as `MoveAsync`: a `TrackerException` that may pass makes it again after each of the `RetryPauses` of the policy, with a line of the log before the try, and the last failure is thrown as it is. A comment goes to the tracker directly and is made once. A kill ends a pause, and after a kill nothing is made again. A kill leaves no task half moved: a kill during the start of a session sends the task back and stops a session the start left, found through `FindStartedAsync`, and once the record of a task is forgotten, as when the tracker is told how it went, and in a pause, the calls of the tracker are made uncut, so that they go to their end; `DoAsync` ends the run as killed when such a task is over, unless the task stopped it over a problem. An uncut call whose pause a kill ends fails with the failure it had. `BringUpAsync` makes the sync again by the same pauses when the remote did not answer. Everything it knows of time comes from `IClock`, so the tests run it start to finish in no time, with a clock that moves only when it is waited on.
- `Outcome` is the line for toobusy at the end of a reply: the contract with the assistant, read here, whether a reply ends with it, with nothing but empty lines after it, which the adapter of the assistant tells with every look as `Reported` and from which alone the run reads how a task went, and whether the report before it names another task, as one of a task done in part must. Its words are written out once more only in the plays of a demo, which are replies as a session would give them.
- `Briefing` is every text toobusy sends to a session, and what it writes into the tracker from what the session answers. The texts are those of the tool and know nothing of a project but what the settings name: the first message begins with the command of the skill of the project, when it has one, and is the same after it.
- `About` is what `toobusy about` prints: how a run works, put together from the messages of `Briefing`, the lines of `Outcome`, the policy and, where there are settings, the rules of the queue, the skill, the branch and the commands around a task, so that it tells what a run does and nothing else.
- `RunPolicy` is the times and the counts of a run, the pauses before a call of the tracker or a fetch is made again among them; a demo has its own. `RunPlan` is what the user and the settings give it: the milestone, the rules of the queue, the model and the effort, the address of the board, the skill a session starts with, the commands of the project around a task, the branch the tasks are done on, the permission mode its sessions work in, which only its log says, and, from the options of `toobusy run`, the one task it does or the number of tasks it takes at most, and the labels it skips, which stand in its rules of the queue: `TaskLineup.Keeps`, which says whether the task of a record is gone on with, does not look at them. `NewTasks` is what of it a session is told to make a new task: the manual label, the labels to take, the milestone and the board.
- `RunLine`, `TaskEnd` and `RunStatus` are what a run tells: a line of its log with the mark of what it tells and, as `Detail`, what the log on disk keeps of it and a screen does not show, the whole of an error nobody foresaw; a task that is over, told once however it ended, with its mark and the time it took; and what the run is doing now, with the commands that mean something at the moment and, while a session waits for the owner, what the session said. `RunResult` says how the run ended and, when it neither ran out of tasks nor was stopped by a command of its owner, why. `RunSign` is what of a `RunStatus` stands on the sign of a run: where the run is, its task, how the session is opened and until when it waits for a usage limit; `Told` says it in a few words, the same for `toobusy status`, for a run that does not start and for the menu.

The adapters know their tools and nothing of a run:

- `GitHubTasks` asks `gh` as the other GitHub adapters do, and the tool itself turns the answers into lines of tab-separated fields. A failure is a `TrackerException` with the first line `gh` said, and it may pass when `gh` did not answer in its time or what it said tells a call that did not reach GitHub, a status of the 500s, a 429, or a rate limit, with what it put between quotes left out, as that is what it was given, the name of a label among it; every other failure stays, and so does an answer that cannot be read whole, as a count of the tasks that is not a number or a line that is not a task, so that a changed output stops a run instead of leaving a task out of the queue. GitHub filters the issues by the number of a milestone: `GitHubTasks` finds it once, by the title, in what `GitHubMilestones.Read` reads of the open milestones and as `MilestoneStanding.Find` finds a title, and keeps it for as long as it lives, which in a run is the whole run. Every read of the queue after that asks for the milestone of that number in the same request as the tasks, and one that is not open any more or is called otherwise is gone, as for the choice of the user, and is found anew when it is asked for again. A board is read by `BoardAddress`, as the settings read it. A long comment goes to `gh` in a temporary file, as the system limits an argument, and a label whose name has a comma or a quote goes quoted as a comma-separated value, as `gh` reads the labels of an option. Every answer of `gh` is read by its lines with `Tsv.Lines`, in all the GitHub adapters. `GitHubCli.Unanswered` says what is said of a call that `gh` gave no answer to, as of a `gh` that is not installed or could not be started, for the adapters that say it. The other GitHub adapters say nothing of that: the commands they serve are run by a person, who runs them again. The statuses of a board are known by the names the settings give them, each the name of GitHub where the settings name none, whatever their case and whatever stands between their letters: `BoardStatuses` of `TooBusy.Core/Queue` is those three names. It tells which status a name of the board is and what a status is called, and says which of the three a board lacks, for the doctor and the setup. The settings hold one, `TrackerSettings.Statuses`, and it goes from there to whatever names a status: to `GitHubTasks`, which reads the status of a task by it and finds the option to move a task to, and through `QueueRules` to the log of a run, to `NewTasks` for the first message of a session, and to `About`. The queue itself knows no names: it takes a task whose `BoardStatus` is `Todo`, which the adapter has told by them. `GitHubSetup.ReadStatusesAsync` reads what a board calls its statuses, the options of its `Status` field, for the two of them and for any command that shows the boards.
- `ClaudeCode` does a task in a background session of Claude Code. It is made with the permission mode of the settings and starts every session in it, with `claude --bg --permission-mode <mode> --permission-prompts none --settings <json> [--model <model>] --effort <effort> -n <name> <message>`: nobody answers a prompt of the session, the settings are those of `ClaudeSettings`, the model is left out for the assistant's own, and the name, the number and the title of the task, is what the session of a start that was cut off is found by. A session that is told to go on, one of an earlier run too, goes on with the options it was started with, which Claude Code keeps for a session it lists, the hook and the status line of its first start among them, and is given no option: a listed session that is given any is started as a copy instead. One that Claude Code does not list any more is given the mode and the settings of a session once more. A copy that Claude Code starts all the same, of a session that something still has, is stopped and removed with `claude rm`, the one session the adapter removes, and the session is tried again, three times at most; a copy of a session that nothing has, by the list, is the session from then on, by its new id and its own conversation. `Telling` says how a message was taken: why it was not, or that it was as a copy. `ClaudeFolders` is where its files are: in the local folder the request of the run, `wrap-up.json`, and what the status line writes, `usage.json`, with the way to make sure of that folder before a request is written into it, and the folder of the conversations of the project; `ClaudeSettings` is the settings a session is started with: a hook that prints the request of the run after every step, a status line that writes the state of the session, the limits among it, to a file, and no worktree. `Transcript` reads the conversation Claude Code writes by its bytes, from the last one it read, so that a line written during a read is read the next time and a character cut between two reads is read whole: the steps of the session; its last reply, and whether the session has reported with it, which a look gives as `Reported`: the reply ends with the line for toobusy, as `Outcome` reads it, and the session did nothing after it; a usage limit; and, from its start, the plan the session keeps as a list of tasks, which a look gives as `PlanStep`s. The session is found in `claude agents --json --all`. That list starts Claude Code, so a look at a session takes it from the last one read, while that is younger than twenty seconds; whatever tells a session something, stops it, starts one or looks for one reads it anew, and a list that could not be read is not kept. A session that is stopped, before it is told something and wherever it is stopped, is waited for until the list has no process for it, twenty seconds at most; `StopAsync` throws an `AssistantException` when the list still has it as working then. A session that the run started or told to go on is given a minute, the `Tolerance`, before a list that cannot be read makes it `Unseen` and one that lacks it makes it `Lost`, as such a session is not always listed at once. A session of an earlier run is found there too, by its id, the one `claude attach` takes, or by its conversation; the list is believed at once for it, and one that is not there is lost at once, and nothing is left of one that no process has and whose conversation is not on the machine: that is found by the file of the conversation, through `ClaudeFolders.Find` as for any look, not by asking Claude Code, which answers a `--resume` of a conversation it does not have by starting a session of that name with nothing in it. The session of a start that was cut off is the one of the list with the name the start gave it, `-n`, and started since the start was made; the list is read a few times for it, as a session that has just started is not always listed at once. When a session is told something, what it said before does not count any more. `ClaudeSkills` says whether a skill is there for Claude Code to load by its command: among the skills and the commands of the project, or among those of the user.
- `ClaudeCodeProtocol` holds what the adapter recognises in what Claude Code prints and writes, with the version of Claude Code it was read against, `Version`: the words of its answers to a start and to a resume, the states of the list of the sessions as a `Standing`, the rule of the folder of the conversations of a project, and what a line of a conversation holds that is Claude Code's own and not the Messages API's: the values of a refusal of the service, the model of what it writes in the name of the assistant, the tools of the plan with the shapes of their results, and the tools that ask. The names of the fields of its JSON are read where that JSON is read, a text of it by `JsonFields.Text`, the one reading of a text in the adapter. `Newer` says whether what `claude --version` prints is a newer Claude Code: `MachineCheckup` gives the doctor the version of the protocol then, as `ToolLook.WrittenAgainst`, and the check of Claude Code is warned of. A state that the protocol does not know is no work: the look says it as its `Odd`, which the run shows in the place of the step and writes into the log, and the session is lost after a minute in it, the tolerance of a list that is silent or lacks the session. The conversation is found by `ClaudeFolders.Find`: in the folder the rule names, or in another folder of the projects of Claude Code, which names the folder of a very long path otherwise. A session that the list has and whose conversation is in none of them a minute after makes the look throw an `AssistantException` that names the file, so that the run stops the session and stops instead of reading silence as a session that says nothing.
- `GitWorkspace` reads the working copy from `git status --porcelain=v2 --branch`: the files, the branch, its upstream and the commits each has that the other lacks. It brings the branch up to date with `git fetch`, which fetches the remote of the branch, and `git merge --ff-only @{upstream}`, which can only move it forward, and only after it has counted the commits again: a branch with commits of its own is not merged at all. A fetch that failed may pass when it did not end in its time, or when what git and ssh said, but for what they put between quotes, tells a remote that was not reached or answered with a status of the 500s or a 429. A login that git, or the Git Credential Manager, could not ask for, as their prompts are off, stays, and git's line of it is what is said of the failure.
- `ShellCommands` runs a line through `sh -c`, apart from `ProcessRunner`, which starts a command without a shell: it gives the command an environment, beside git's prompts off as `ProcessRunner` does, keeps what it printed to both streams as one text, read as UTF-8, also of a command that is stopped for its time, and does not wait for what a command left running with its output open.
- `LocalFolder` is `.toobusy/local` of a project, which keeps itself out of git with a `.gitignore` of its own whenever it is made, by whoever makes it: everything that writes into it, `RunStateFile`, `RunSignFile`, `RunLogFile` and the request of `ClaudeCode`, `wrap-up.json`, makes sure of it with `LocalFolder.Make` before it writes, so that a folder taken away while a run goes on, by a `git clean -fdx` of a session or a script of the project, comes back with its `.gitignore` and the next task does not find the working tree unclean over the run's own files. `ClaudeCode` cannot reference `TooBusy.Infrastructure`: `ClaudeFolders` takes the way to make sure of the folder, which `ProjectRuns` wires to `LocalFolder.Make`. `LocalFolder.State` and `LocalFolder.Sign` give the record and the sign of the project at a root, for a run and for `toobusy status` alike. `RunStateFile` is the record there, `session.json`, put in place whole. `JsonFields` is what it and `RunSignFile` read and write of their JSON alike: a text, and a moment in UTC. `RunSignFile` is the sign of a run there, `run.json`, with the number of the process of the run and when that process started: it reads a sign as a `GoingRun` only while that process lives and started then, which it asks the operating system through `System.Diagnostics.Process`, so what a run that died left behind is not read, and it takes down no sign but its own and one that says nothing: of a process that died, or that cannot be read. It looks at the sign and puts its own up while it holds `run.lock` beside it, opened with `FileShare.None`, which the operating system gives to one process at a time and takes back from one that ended: two runs started together cannot both find no sign, or a dead one, and both put theirs up. A lock that another run holds is waited for, up to two seconds, and the file is never taken down, as a lock file that is taken down and made anew can be held by two processes at once. `RunLogFile` is the log of a run there, `logs/run-<date>-<time>.log`, written line by line, with the time of day on every line, and pruned to the last ten when a log opens; it throws nothing into the run, and a log that cannot be opened or written says so once. `LoggedRun`, `LoggedView`, `LoggedProcesses` and `LoggedCommands` are what writes into it, around the run, its view, the runner of the machine and the commands of the project: the lines of the run with what a screen does not show, every command with how it ended, how long it took and what it answered, as `Printed` cuts it: whole when it failed, and when it passed only when it is short and not JSON; a command that passes again right after itself counted in one line that `RunLogFile` holds until the next text; how the run sees its session, as `Trace` tells it; and how the run ended; `LoggedRun` names the log under every run and closes it.

`Workbench.Runs` is what the runs of a project are made of, an `IProjectRuns` of `TooBusy.Cli` that `Workbench` chooses once when it is opened: the open tasks a run reads, its record, the sign of a run that goes on, and a run itself, so that `run`, `queue` and the menu read the same queue and the same record, real or imitated, without asking which. `ProjectRuns` puts a run together of the real adapters, with the log of the run around them, the tasks of the `origin` repository through `GitHubTasks`, and the record and the sign of the local folder; without a GitHub repository it reads no tasks and opens no run. `ImitatedRuns` is the real `Supervisor` over made-up tasks, the fifteen of a small online shop, and sessions that are plays written in the code, lasting as long as the clock says, and gets no log; it keeps the made-up tasks and the record in memory for as long as the demo goes on, and makes the tasks up anew, forgetting the record, when the settings were changed in the demo so that the tasks no longer fit their labels, their board or its statuses; it reads no sign, and takes a moment over counting the tasks for the menu where somebody watches.

## Settings

The settings of a project live in three places:

- `TooBusy.Core/Settings` holds the model (`ProjectSettings`, a record for each section of the file: `TrackerSettings`, `QueueSettings` with its `LabelSettings`, `AssistantSettings`, `SessionSettings`, `TaskCommands` and `WorkspaceSettings`), the names of the keys (`SettingsKeys`) and the validation rules (`SettingsValidator`). `BoardAddress` is the address of a board in its parts, the one rule of what a board is, which the validator, the setup and the GitHub adapters read it by. The validator knows nothing of TOML: it takes a `SettingsDocument`, every value under its full dotted key with the line it is written on, and gives back the settings or the errors, each with its key and, where the file has a place for it, its line.
- `TooBusy.Infrastructure/Settings` reaches the disk. `ProjectLocator` walks up to the root of the git working copy, `SettingsFile` is `.toobusy/settings.toml` at that root, and `SettingsToml` turns TOML text into a `SettingsDocument` and settings back into text.
- `TooBusy.Cli` asks for the project and its settings before a command runs, prints the "not set up" message, and maps the outcomes to the exit codes in `ExitCode`. A command that fails writes its lines where errors go and returns its exit code itself, where it fails: no helper picks one for it, so that the code of every failure stands next to it. `CliApp.RunAsync` says an error that a command did not foresee in a `toobusy:` line where errors go and exits with code 1, instead of the stack trace of `System.CommandLine`; `Guarded`, around the action of every command that can be cancelled, tells such an error from the cancellation of the user, which it lets through. The trace is printed when `CliContext.Trace` asks for it, which is `TOOBUSY_TRACE=1`.

TOML is parsed with [Tomlyn](https://github.com/xoofx/Tomlyn), through its syntax tree only (`SyntaxParser`): the tree keeps the place of every value, and nothing of it needs reflection. The object serializer of Tomlyn is not used. Writing does not print the tree: `SettingsToml.Write` edits the existing text at the places the tree names, replacing a value that differs, removing the line of a key the settings have no more, adding a missing key at the end of its section, or before everything else when it has no section, and a missing section, with its comment, at the end of the file. Everything else, comments and unknown keys included, stays character for character, and a new file is the same edit of an empty text. The result is parsed again before it is returned; a layout that cannot be edited this way, such as a section written as an inline table, is refused with a `FormatException` instead of being written wrong, and so is a text that is not TOML. `SettingsFile` then writes the file anew, as it writes a first one, and puts it in place whole: it writes a file beside it and moves that over it.

## Setup

`TooBusy.Core/Setup` holds the steps of `toobusy init` (`ProjectSetup`) and the ports they are written against, but for the store of the settings, which stands with the settings:

| Port | What it hides | Implementations |
|---|---|---|
| `ISetupDialog` | showing the notes, the answers and the place among the steps; asking: a selection, a multiple choice, a text, the board, a confirmation; waiting for something that is read. Every question can be gone back from, and so can a wait: the reading is told to stop | `SetupScreen` in `TooBusy.Cli`; a scripted one in the tests; none for `init --yes`, where `ProjectSetup` takes what every question proposes |
| `ISetupEnvironment` | what is installed and logged in, the `origin` remote, and whether a skill is there, a `SkillLook` | `MachineEnvironment` in `TooBusy.Cli`, which runs the checks of the doctor that need no settings, adds the `origin` read by `GitOrigin` of `TooBusy.Infrastructure` and asks the machine of the doctor for the skill; imitated in a demo, where the repository is that of the made-up project and every skill is there |
| `ISetupTracker` | whether a board can be read, what it calls its statuses, the labels; making a board, linking one to the repository and making a label, which throw `TrackerException` when GitHub refuses | `GitHubSetup` in `TooBusy.Trackers.GitHub`; imitated in a demo |
| `ISetupBoards` | the boards the user can reach, those linked to the repository, and who a new one can belong to, or that the tracker did not answer for them in time | `GitHubBoards` in `TooBusy.Trackers.GitHub`, which asks `gh` through `IProcessRunner`; in a demo `ImitatedBoards`, the made-up ones |
| `ISettingsStore`, in `TooBusy.Core/Settings` | the settings file: loading, the text before and after a change, saving | `SettingsFile` in `TooBusy.Infrastructure`; in a demo `UnwrittenSettings`, which reads no file and remembers instead of writing |

`TooBusy.Core/Queue` holds the milestone to work on. It is the choice of the user, not a setting of the project. `TooBusy.Core/Assistant` holds two more such choices, the model and the effort the tasks are done with by default: `ModelChoice`, and `ClaudeCodeOptions` with the models and the levels that are offered. `ClaudeCodeOptions` holds the permission modes a session can be started in too, which are a setting of the project and not a choice of the user, with why the others are refused and, as `Checks`, what each checks, in the words that the question of the setup and `About` both say. The lists are those of Claude Code, the only assistant so far, and they stay in Core until the port of the assistant is asked for them. The choices have two ports:

| Port | What it hides | Implementations |
|---|---|---|
| `IMilestones` | the open milestones of a repository | `GitHubMilestones` in `TooBusy.Trackers.GitHub`, the one reading of them, by lines that the tool writes with `@tsv`, so that a title with a tab is one field: `GitHubTasks` finds the number of its milestone by it too; in a demo `ImitatedMilestones`, the made-up ones |
| `IPersonalSettings`, in `TooBusy.Core/Settings` | where the choices of the user are kept: the milestone, the model and the effort, each one apart | `PersonalSettingsFile` in `TooBusy.Infrastructure`: `projects.toml` of the user's own toobusy folder, a table for each project, read and put in place whole while it holds `projects.lock` beside it, as `RunSignFile` holds its lock, so that two toobusy that save a choice at once keep both; in a demo `UnsavedChoice`, which forgets |

`MilestoneStanding` says where a choice stands against the open milestones: not made, open, no milestone, gone, or not checked because the milestones cannot be read. `MilestoneOrder` is the order milestones are offered in.

`ProjectSetup` is a walk over its steps: an answer moves it forward, going back from a question moves it to the step before, and going back from the first one leaves the setup. It keeps the answers in one `SetupAnswers`, an immutable record that every answer replaces and that holds, for a question not answered yet, what the question proposes: a step that is asked again proposes what was answered, the menu takes up the answers a page showed by taking that record back, and the settings are made of it. The statuses of a board are a `StatusesAnswer` in it, with the board they were named for, whether they were asked for and what is said of them; going back from their first question leaves the record as it was. Nothing is changed before the last step is confirmed; a new board is an answer like any other until then.

The same steps serve `Settings` of the menu one setting at a time. `OpenAsync` looks at the machine and reads the settings as the walk does, `Values` are the settings as the menu lists them, a `SetupValue` for each `SetupSetting` with how its value looks, the statuses of a board among them as `BoardStatuses.Told` says which is which, and `ChangeAsync` asks the questions of one setting with the answers of the others as the settings have them: the questions of `init`, those of the statuses whatever the board calls them, and for the commands around a task, the branch and the permission mode questions of their own. What is answered goes through the same last page, which in the menu decides by the settings whether anything changes, does on GitHub only what that setting needs, and asks `Save the change?`; going back from it asks the setting again. `SetupProgress.Menu` tells the dialog that a question is of such a setting: there are no steps, and going back from its first question gives what is chosen or typed there as the answer, so that a setting that is left changed is asked about too. A question of the labels offers every label with its roles in the other settings, a `SetupOption` that is off where a role keeps it out, as `RolesOf` tells: in the menu by all the other settings, in the walk by the steps before it, whose order keeps the answers right. The menu keeps the manual label out of the blocking labels, where it keeps out nothing more. `Changed` is what the menu saved, for the report.

The options of `init` reach the steps as `SetupProposals`: what an option says is proposed before the value of the settings and before what a first setup proposes. The board of an option is checked when the boards are read and its labels when the labels are, once. `--yes` is the same walk without a dialog: `ProjectSetup` then answers every question with what it proposes and the last one with a yes, so a setup that asks nothing does what one does where Enter is pressed all the way. The question about the board is where the two can differ: with no board to keep and none proposed, the screen opens on the list of the boards, where Enter takes the first of them, and a setup that asks nothing takes no board. What an option says and cannot be is a warning among the notes where somebody is asked, and where nobody is it ends the setup as failed, before anything is changed; so does a proposed text that its question refuses, and a board that cannot be read. The result carries the notes and a line for each thing that was done on GitHub, which `CliApp` prints as plain lines.

The setup never asks for the repository: `ISetupEnvironment` gives the one of the `origin` remote, and the labels are read from it. A board that is chosen has its statuses read through `ISetupTracker`, and the step of the board goes on with which of them is which: three questions of the same step, asked through `ISetupDialog` as a choice among the statuses, or as a typed name where nothing is verified, and not asked at all over a board that has the names of GitHub. `SetupProgress.Later` tells the dialog that such a question is not the first of its step, so that going back from it does not leave the setup. A board that cannot be asked about, with fewer than three statuses or in a setup that asks nothing, is taken with a warning on the last page and among the notes of the result. Nor does it make the skill it asks the name of: it asks `ISetupEnvironment` whether the skill is there, and says where it is to be written when it is not. `BoardSuggestions` is what the question about the board does with a typed text: it finds the boards that fit it and turns the address of any page of a project into the address of its board.

`Assist` is what `toobusy init --assist` prints: the walk through the setup for the assistant of the owner. It stands beside the setup as `About` stands beside the run: a function of how the project stands, an `AssistGround`, that gives the text of the introduction or of one step, with nothing of the terminal in it. The ground is the settings as they were loaded, the choices of the user, what is found of the skill, what the sign of a run says, and, for a step that chooses among what the tracker has, one reading of it: `Assist.Reads` says which, the labels, the boards with their statuses or the open milestones. What a command of a step proposes to call the two labels and the skill is what `ProjectSetup` proposes in a first setup. `Workbench.AssistAsync` reads the ground through the ports the setup and the doctor read through, and changes nothing; it asks whether `gh` is there and logged in before anything of the tracker, so that a step can say why something is not read. `CliApp` checks the number and that no other option stands beside `--assist`; with `--demo` the ground is that of the made-up project before a setup.

`Workbench` in `TooBusy.Cli` is where these ports are put together for a project, in one place: `Workbench.OpenAsync` puts the real adapters together over the root of a project, and `Workbench.OpenDemo`, for `--demo`, which `CliApp` gives every command but `about`, the imitations of `TooBusy.Cli/Imitation` over the made-up project of a demo, `DemoProject`: its folder as the bar names it, its repository, its board, its labels and the settings of a demo that is ready. A demo is the real steps and the real screens over a machine where everything is installed, a tracker with the made-up repository, labels, boards, owners and milestones, which makes and links nothing, settings that are remembered instead of written, and choices of the milestone, the model and the effort that are forgotten when the demo ends. It needs no root, and reads nothing of the folder it is run in or of the machine: `CliApp.OpenAsync` finds no project for it and gives it no runner of commands, so the same demo comes out everywhere. The demos that show a project that is ready, `toobusy --demo`, `run --demo`, `queue --demo` and `doctor --demo`, start with the settings of `DemoProject` and with the choices made; the others start with no settings and nothing chosen. The labels of the demo are those of toobusy's own repository, by choice, with `design` besides: `feature`, `bug`, `chore` and `docs` to take, `draft` and `design` that block, `manual` and `interrupted`, and the skill `task-auto`, so that a demo looks like a project that works as toobusy itself does. Nothing depends on them: the made-up tasks take the labels of the settings, which the menu of a demo may change. `Workbench.OpenDemo` is told whether a page shows what is read while it is read: the boards of a demo and the count of its tasks for the menu take their time only then, so that the wait can be looked at, and `init --demo --yes` and `queue --demo` wait for nothing.

`Session` is what happens on the page from the moment it is opened: the setup when the project needs it, the choices of the milestone, the model and the effort when the user has none, the menu and the run, each a screen that takes the page for a while. A run that is opened from the menu comes back to it; `toobusy run` runs the queue alone and leaves. `Settings` of the menu opens one `ProjectSetup` for as long as its list is on the page, and a `SettingsScreen` over it; settings that do not validate get the walk of `init` instead, as a project that is not set up does. What it saved is the setup the report tells, kept as soon as a change is saved. Before the menu opens a run, outside a demo, `Session` makes the checks of the doctor and gives them to the menu as `RunChecks`, the view of the checks that the menu watches; the checks that failed go into the body of the page, above the menu, as the lines `CheckList.Told` makes of them. An error that stops the checks, other than the stop of the menu, is one more check that failed, so that the menu opens no run where `toobusy run` would start none. The setup of `Settings` is opened in the same way, under the menu, as a `HomeWork`: both are an `IHomeWait`, what a row of the menu waits for before it opens, which `HomeScreen.WaitAsync` shows at its row until the wait is over and the menu gives that row by itself. Another row that is chosen meanwhile is what `Session` goes on with, and Escape gives nothing and the menu is asked again; either way the work that was not waited for is told to stop and left to it. A screen of it that says nothing at the right of the bar, as the menu, says the version of the tool there: `CliApp.Version`, the one place the version is read from, which `--version` prints too, with `CliApp.Commit` after a plus in a build in development. It remembers what was done for the report that `CliApp` leaves in the terminal, which says nothing of a run again: a run leaves its own tape there. `CliApp.WithPageAsync` opens the page for a `Session` and closes it however it was left, and each command that opens one writes its own report from the session it gives. `Workbench.ReadQueueAsync` reads the queue as a run does before a task and changes nothing: the lineup, with the task of the record before the others when a run would go on with it. `Workbench.OutlookAsync` says from it what a run would take, for the menu: how many tasks, and the one it goes on with first, the task of the record or an interrupted one. Both take the labels a run skips: those of `run --skip-label` and `queue --skip-label`, or those `Session` keeps from `Skip labels` of the menu for as long as the page is open, and nowhere else. `Workbench.ReadLabelsAsync` reads the labels that the menu offers to skip, as the setup reads them, after it has asked whether `gh` is there and logged in, so that the list can say why it has none. `toobusy queue` prints the same lineup whole. `Workbench.Going` is the run that goes on in the working copy, by its sign: `toobusy run` and `Run` of the menu ask it before the checks and open no run while there is one. `toobusy status` asks for no `Workbench`: it reads the sign and the record of the local folder, through `LocalFolder.Sign` and `LocalFolder.State` as `ProjectRuns` does, and nothing else.

## Doctor

`TooBusy.Core/Doctor` holds the checks of everything a run needs. `Checkup` runs them in their order and knows which check waits for which: `MachineAsync` is the five that need no settings, the tools and their logins, and `RunAsync` adds the settings, the repository, the board, its statuses, the labels and the skill a session starts with. A check ends as a `CheckResult`: passed, warned of, failed or skipped, with what it found, what it warns of or what is wrong and, for a failure, its fix. A warning fails nothing: a tool that runs and is newer than the version toobusy was written against, which its `ToolLook` names as `WrittenAgainst`, passes with one. `Fixes` is the table of the fixes, a function of the tool, the platform and whether its package manager is there. The checks read the settings through `ISettingsStore`, and have two ports of their own:

| Port | What it hides | Implementations |
|---|---|---|
| `ICheckupMachine` | the platform; whether `git`, `gh` and `claude` run, why one that is there cannot be started, and the version toobusy was written against when the one that runs is newer, as a `ToolLook`, and whether a package manager is on the path; the login of the tracker, as one that is there, one that is not, or one the tracker did not answer for in time, and the login of the assistant; whether the repository and the board can be read; what the board calls its statuses; the labels of the repository; whether the assistant has a skill | `MachineCheckup` in `TooBusy.Cli`, which asks the tools for their versions through `IProcessRunner` and puts together `GitHubCli` and `GitHubSetup` of `TooBusy.Trackers.GitHub` and `ClaudeLogin` and `ClaudeSkills` of `TooBusy.Assistants.ClaudeCode`; in a demo `ImitatedCheckup`, a machine that has it all |
| `ICheckupView` | where the checks tell that one starts and how each ends | `CheckList` in `TooBusy.Cli`; `NoCheckupView` where nobody watches, as in the setup |

`Workbench.Checkup` puts them together over the settings and the `origin` remote of the project. `toobusy doctor` shows every check, `toobusy run` and `Run` of the menu run them before a run starts and tell the failures only, and `MachineEnvironment` turns the failed ones of the machine into the notes of the setup.

## Terminal

`TooBusy.Cli/Terminal` is everything that knows it talks to a terminal.

- `Palette` is the one place that defines colours: the accent, the error, success, the warning and muted text, each for a dark and a light terminal in truecolor, as the three numbers of a colour from which every code of it is made, the blinks that fade between two colours among them, and as one of the sixteen colours for a terminal that does not announce truecolor. `Palette.Detect` gives the palette without colours when `NO_COLOR` is set, the stream is not a terminal, or `TERM` is `dumb` or not set. Commands never write an escape sequence of a colour themselves.
- `TerminalDevice` is the terminal as a screen needs it: its keys, its size, taking Ctrl+C as a key, watching the size of the window, and a timer.
- `Screen` is the alternate screen, entered with the first frame that is drawn. It draws a frame whole every time: the bar with the title and the status, the body, the question, the choice and the keys with a rule between them, and the foot, each line cut to the width. What waits for the user is drawn by the screen and blinks: the name on the chosen line of the choice, which is the first piece of that line, and the block where a text is typed. `Pulse` counts the beats, eighty milliseconds each, and rewrites only that line and that cell in the shade of the moment; drawing a frame does not start the count again. The same beat moves the light along the dots of a wait, the line that `Page.WaitAsync` puts under what is being read: `Screen.Spark` says how brightly a dot is lit at a step. The foot is wrapped to the width, never cut. `TerminalDevice.Every` is the timer behind it, so that tests move the pulse by hand. It keeps the last frame to draw it again when the size changes. The dots of a wait may stand after a name on a row: the screen finds them in the line. `Screen.Rescue` is what a program that is stopped from outside must still write, whatever has the terminal at the moment; a tape that had it is abandoned then and draws nothing more, as what was written under its foot has taken the cursor away from it.
- `Tape` is the terminal's own screen written as a tape, for a run: `Screen.Unroll` leaves the alternate screen and prints the bar once; what is settled is written for good and scrolls into the history of the terminal, and the foot, a `Strip`, is drawn over itself under it: the cursor goes up to its first line, every line is written again, and what is left of a longer foot is erased. Nothing above the foot is erased while the window keeps its size. The tape remembers what it has settled, as pieces that lay their lines out to a width: when the size of the window changes it erases the terminal with its history and writes the bar, all of them and the foot anew. Lines are cut a column short of the window and the terminal is told not to wrap, because a line the terminal broke would make the foot taller than it is counted. The tape shares the lock and the beat of the screen: the mark of the foot turns, and its chosen line, its cursor and the lit cells of a bar blink, written where they stand by moves counted from the line the cursor rests on. The next frame rolls the tape up and enters the screen again.
- `Page` is what every screen of the tool shares: it takes the terminal and gives it back, puts the body, the status and the foot it is given around the question of the moment, and reads the keys. Ctrl+C twice in a row throws `OperationCanceledException`, which the command that opened the page catches; `GiveBackControlC` makes Ctrl+C the terminal's own again for the rest of the page. While more keys are waiting, as in a paste, it does not draw. `WaitAsync` runs something that takes a moment under the dots of a wait and goes on reading the keys meanwhile, looking for one every thirty milliseconds, so that `Back`, Escape and Ctrl+C work before the work ends; work that is not waited for gets its cancellation and is left behind.
- `SetupScreen` is the setup on a page, `MilestoneScreen` the list of the milestones, `ModelScreen` and `EffortScreen` the lists of the models and of the levels of effort, `HomeScreen` the menu, `AssistantScreen` the list its `Assistant` opens, `SettingsScreen` the list its `Settings` opens, every setting with its value, and `SkipScreen` the multiple choice its `Skip labels` opens. The board question of `SetupScreen` is a tab for each way to name a board, the known boards, an address, a new board and none, each a `BoardTab` that shows its own lines and takes its own keys; the question draws the tabs and a place under them as tall as the tallest tab, where a list starts at the top and anything else stands at the bottom, and keeps Tab and Escape for itself.
- `RunScreen` is the page of a run, on a `Tape`: the tasks that are over and what the run warns of stay, and the foot is the task that is worked on, with the plan of its session as a bar under it, the menu of the commands between two rules, whose pointer says where the menu opens or that the run stops or aborts, with the usage limits at its right, and the keys, which name `/` while no menu is open, with the place of the task among the tasks of the run, which `RunStatus` gives as the tasks over before it and those that follow it. The run goes on by itself on another thread and never touches the page: it speaks into a `RunFeed`, and the page takes from there what was said when it draws. The page waits for a key with `Page.ReadAsync`, which looks for one again and again and gives up when something changed, so that the foot is drawn anew; a foot that would show the same is not drawn. When the run is over the page writes how it went and gives the result; however the page is left, the run is killed and never left to go on alone. A run that is killed is drawn on until it is over, with a foot that says that it stops and keys that do nothing, as what the kill does not cut may wait for the tracker; a page that was left gives Ctrl+C back meanwhile, so that one more reaches the termination handler of System.CommandLine, which waits thirty seconds at most. `RunLook` is what a run looks like: the lines of its log, the line of a task that is over, the bar of a plan, the summary. `PlainRun` prints the log where there is no terminal. `Picker` is the list the screens share: a row is a pointer, a name, what explains it and what is to be noticed about it, and a list that does not fit scrolls between marks. `Picker.Up` and `Picker.Down` are the keys that move a pointer, in its lists and in the menu of `RunScreen` alike; the board question keeps Tab for its tabs, and a tab where a text is typed moves with the arrows alone. A choice may be off, and may wait: `PickAsync` draws the list again when what it waits for is done, as the menu does while the tasks are counted, and what goes on may choose a row by itself, as the checks before a run choose `Run` when they are over and the settings that are read choose `Settings`. Where Escape goes back and does not leave the page, a list ends with `Back`, which names its key: `Picker` adds the row by itself, and the lists that `SetupScreen` draws on its own ask it whether to. A `Choice` that is the one of now has `current` right after its name, in a column that the other rows of its list keep: a `SetupOption` of the setup says it is that one, a `BoardQuestion` names the board of the settings, and the lists of the milestone, the model and the effort know it from the choices of the user. A list without choices and without `Back` says that there is nothing to choose from, and only Escape leaves it. `Picker.Answer` is the line of something that is settled, with its label in a column of its own; the report a command leaves in the terminal prints the same lines with `Line.Painted`, so that the two do not drift apart. `PickMany` is its multiple choice, of the setup and of `SkipScreen`: an option that is off is muted and is not chosen, and the mark of one that is current is in the colour of success, a steady `Part` among those that blink, as the `Blinking` of its line counts them. `Prompt` is the question that is answered with a text. Both can keep what is chosen or typed when they are left, for the first question of a setting of the menu: going back gives it as Enter does. `LineEditor` is the text of a field and the caret in it; it knows nothing of the screen.
- `CheckList` is the checks of the doctor as lines on the terminal's own screen, outside the alternate one: a mark, the name in a column as wide as the longest of `Checkup.Names`, and what was found, and the fix under a failure. In a terminal the check that is running has a line with the sign of a tape, which turns with the same beat and is erased when the check ends: `CheckList` writes that line over itself with `\r` and erases it with `\x1b[K` on its own, outside `Screen` and `Tape`, as it has no screen; a list of failures only, as a run wants it, writes them where errors go and leaves nothing of the rest.
- `QueueLook` is what `toobusy queue` prints: the three lists of a lineup as lines, with the numbers and the titles in the same columns, and the same as JSON, written with `Utf8JsonWriter`. It has no screen: the lines go to the output as they are.
- `StatusLook` is what `toobusy status` prints: the line of a run that goes on, or that none does with the task of a record, and the same as JSON, written with `Utf8JsonWriter`; and the made-up run of its demo.
- `CliContext` carries the folder, the streams, their palettes, the terminal device, the process runner, the clock, the home folder, the folder of the user's own settings and the variables of the environment into the commands, so that tests run them with string writers, scripted keys, a faked `git`, `gh` and `claude`, a clock that makes nobody wait, and an environment of their own, in which no variable is set that a test does not set itself: a test never follows the `CLAUDE_CONFIG_DIR` of the machine it runs on into the folder of Claude Code there.

The screens are drawn by hand with the escape sequences every terminal knows. Spectre.Console was the first candidate and was not taken: the setup needs the whole window, with a panel that stays at its bottom, and its prompts write below one another.

The tests read a screen as text. What it looks like is checked with `tools/screenshot.py`: it runs the real binary with `--demo` in a pseudo-terminal, presses the keys of a scenario, draws the screen to pictures in a new folder of `artifacts/screens`, the rows that blink at several moments of a blink, and ends the binary with Ctrl+C. The length of a blink it reads from `Screen.Beat` and `Screen.Beats` in the source. It is a Python script with its own environment for a terminal emulator and a drawing library; nothing of it is part of toobusy.

## Adding a tracker or an assistant

A new project `TooBusy.Trackers.<Name>` or `TooBusy.Assistants.<Name>` implements the ports and gets a rule in the architecture tests.

Nothing chooses an adapter by its name yet. `Workbench`, and the `ProjectRuns` it chooses, put the GitHub and the Claude Code adapters together whatever `tracker.type` and `assistant.type` say, and the validator lets them say `github` and `claude-code` only: the two names are constants of `SettingsKeys`. A second adapter brings that choice into `Workbench` and its name into `SettingsKeys`. Core and the CLI change with it too, where they still know the only tracker and the only assistant. These are all such places, and a change that makes another one names it here.

The tracker, in Core:

- `BoardAddress` of `TooBusy.Core/Settings` is what the address of a GitHub board looks like: the one rule that the validator, the setup, `GitHubBoards`, `GitHubSetup` and `GitHubTasks` read a board by. `BoardSuggestions` turns the address of any page of a GitHub project into the address of its board, and `BoardStatuses.Default` is what GitHub calls the statuses of a new board, which the validator and the setup name where the settings name none.
- A repository is GitHub's `owner/name`: `RepositoryName` reads it from a GitHub remote, `ISetupEnvironment` gives it as that, and `Checkup`, `ISetupTracker`, `ISetupBoards` and `IMilestones.ReadOpenAsync` take it. A second tracker gives them a handle of its own.
- `Outcome.Naming` is how a GitHub report names a task, `#34` or the address of an issue, by which the run tells whether the report of a task done in part names the task of what is left. It moves behind the tracker: `QueueTask` carries whether a text names a task, or `ITaskTracker` is asked.
- `BoardAccess.LacksScope` of the ports of the doctor is the scope of a GitHub token, which `Checkup` tells and `Fixes.ProjectScope` puts right.
- The doctor names its checks of the tracker by `gh` and its login, `Checkup.TrackerTool`, `Checkup.TrackerLogin` and `Tool.GitHubCli`, says what it finds of them, of the repository and of the board in the words of GitHub, and `Fixes` installs `gh` and logs it in.
- The setup: `ProjectSetup.ProjectHint` names the GitHub project of the tasks, the notes and the refusals of its steps say that GitHub did not answer, cannot be read or gives a new board its statuses, its last page tells `Tracker · GitHub`, and `SetupAnswers` writes `github`.
- The log of a run says that GitHub did not answer when a call of the tracker is made again.
- `Assist` tells of `gh`, of the GitHub repository of the `origin` remote, of its boards and of its logins.

The assistant, in Core:

- `ClaudeCodeOptions` holds the models, the levels of effort and the permission modes of Claude Code, the mode a session is started in when the settings name none, which `AssistantSettings.SessionMode` and `RunPlan` take, and `Checks`, what a mode checks, which the question of the setup and `About` both say. The validator knows the permission modes by the assistant of the settings, so a second assistant brings its own modes there.
- `Briefing` tells a session how to work in the words of Claude Code: not to enter plan mode, to keep a plan of the work in its task list, and what a subagent that reads a message does.
- `About` names the instructions and the folder of the skills of Claude Code, `CLAUDE.md` and `.claude/`, and says what its permission modes check; `Assist` tells of the files, the skills, the settings and the permission modes of Claude Code.
- The doctor names its checks of the assistant by `claude` and its login, `Checkup.Assistant`, `Checkup.AssistantLogin` and `Tool.ClaudeCode`, and `Fixes` installs it and logs it in.
- The last page of the setup tells `Assistant · Claude Code`, and `SetupAnswers` writes `claude-code`.
- The log of a run says that Claude Code marks a session as waiting for an answer, and that Claude Code started a copy of a session that goes on.

`TooBusy.Infrastructure`: `GitOrigin` reads the `origin` remote as a GitHub repository, `SettingsToml` says in the comment of the statuses that a status the settings do not name is called as GitHub calls it, and `PersonalSettingsFile` reads the effort by the levels of `ClaudeCodeOptions`.

The CLI, which puts the adapters together and so knows them by design:

- `Workbench` and `ProjectRuns` make the GitHub and the Claude Code adapters and follow `CLAUDE_CONFIG_DIR` through `ClaudeFolders`; `MachineCheckup` asks `git`, `gh` and `claude` for their versions and puts `GitHubCli`, `GitHubSetup`, `ClaudeLogin`, `ClaudeSkills` and `ClaudeCodeProtocol` together for the doctor.
- `Workbench.AssistAsync` and `Workbench.ReadLabelsAsync` say that `gh` is not installed, could not be started or is not logged in to github.com, and that GitHub did not answer.
- `CliApp.NoTasks`, `Session` and the `milestone` command say that the `origin` remote is not a GitHub repository, `MilestoneScreen` that the milestones cannot be read from GitHub, and `SetupScreen.Ending` that GitHub is set up as the settings say; the help of `--board` and `--new-board` names a GitHub project.
- The help of `--permission-mode` tells what the modes of Claude Code check, and `ModelScreen`, `EffortScreen` and the `effort` command offer the lists of `ClaudeCodeOptions`.
- `StatusLook.MadeUp`, the run of `status --demo`, and the sessions of `ImitatedRuns` are opened with `claude attach`, and `DemoProject`, the made-up project of a demo, is a GitHub repository whose tasks have the addresses of GitHub issues, with GitHub boards of a user and an organisation.

## Native AOT

The tool ships as a native binary, so every source project is built with `IsAotCompatible` and warnings are errors. In practice:

- no reflection-based serialisation: JSON is read with `JsonDocument` and written with `Utf8JsonWriter`, and nothing is serialised from objects;
- no libraries that need runtime code generation or are not trim-safe;
- command-line parsing with `System.CommandLine`;
- TOML with the syntax tree of Tomlyn, which publishes without warnings;
- globalisation is invariant: output does not depend on the machine's culture.

A dependency is added only after checking that it publishes without AOT warnings.

## Conventions

- macOS and Linux are what the tool runs on for now. Windows is not built: a command of a project runs through `sh -c`, the hook and the status line of a session are POSIX shell commands, and nothing sets the console to UTF-8. [#89](https://github.com/bitpatch/toobusy/issues/89) lists what Windows needs, for when somebody runs the tool there. A branch for a platform comes with a test that runs it, and not before; the fixes of the doctor name those of Windows, which their tests check.
- How long a command of the machine is waited for is a constant of the class that runs it, mostly its `Patience`, and the times of a run are those of `RunPolicy`. SPEC lists every such time in "How long a command is waited for", so a change of one changes that table too.
- .NET 10, C# latest, nullable enabled, warnings as errors.
- Package versions live in `Directory.Packages.props`.
- Tests use xUnit v3. A test class that grows large is split by what its tests are about. The tests of `Supervisor` are one partial class over the fixture in `SupervisorTests.cs`, with a file for each concern, as `SupervisorTests.Branch.cs` and `SupervisorTests.Stop.cs`. The tests of the commands of the CLI are a class for each command, as `RunCommandTests` and `MenuTests`, over `CliAppTests`, which holds the project, the machines and the runs of the tool that they share; xUnit runs the classes in parallel.
- A test says what it depends on, so that a change that keeps the behaviour fails no test that is not about it. The tests of `Supervisor` run by a policy of their own, set whole in the fixture with round times unlike one another, and compute every time they expect from it, as `Spoken.Time(policy.OwnerWait)`, and the moments they plan from `AfterLook`. They compare what the tracker was told in any order, with `AssertDid`; only the tests of the orders that are behaviour, the report in a task before it is closed and the label of a task before it goes back to `Todo`, read `tracker.Did` in its order. A play of `FakeSession`, whose rules its header states, that the run does not come to the end of fails the test. A screen test goes to a line of a list with `Keys.Until`, by what the line says and not by counting arrows, and finds a row of a frame with `TestTerminal.RowOf`; `PageTests` counts the rows of a page in one place. The commands of the machine are answered in each test project by its `ScriptedProcesses`, which fails a command it has no answer for with the command named; the tests of Claude Code have `FakeClaude`, which keeps the list of the sessions of `claude` and does the same. `GitWorkspaceInARepositoryTests`, which runs the real git, gives the git of the test and that of the tool `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`, so that no configuration of the machine changes what they see, and is skipped with a message on a machine where git cannot be started. A test of `ProjectSetup` that runs a setup again calls `Reset()` before it, which forgets what the fakes saw and did and keeps what the test set them to, so that what each setup did is seen alone.
